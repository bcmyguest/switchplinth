# Project orientation

Read `AGENTS.md` and the specifications in `docs/` before implementation. `docs/V2_PLAN.md` is the current plan. Decision is the domain object; ADRs and other Markdown are source artifacts. Markdown and validated `.decision/` YAML are canonical. SQLite, Qdrant, model workflow state, and graph indexes are disposable.

## Runtime

Docker Compose runs separate `frontend`, `backend`, and `qdrant` services. The frontend is React/TypeScript with Tailwind and shadcn/ui. The backend is Python 3.12/FastAPI. Published ports bind to loopback. The backend maps `host.docker.internal` to the Linux host gateway for local model connections. Local API docs are at `http://localhost:8000/docs`, the frontend at `http://localhost:3000`, and Qdrant at `http://localhost:6333`.

## Backend boundaries

The deterministic domain/compiler does not depend on HTTP, SQLite, Qdrant, or model providers. Keep provider-neutral connection records portable and secrets out of YAML. Blank optional connection fields are omitted from saved `model_connection` records; explicit `env:` credential references are preserved. Local `openai_compatible` extraction can run without a credential reference; hosted OpenAI and Anthropic connections use their configured credentials. Inferred claims and aliases need evidence; human reviews append records and supersede earlier human judgments without rewriting the original inference. Keep source anchors relocatable and avoid line numbers as identity. Options are typed deltas over one base graph. YAML edits, API graph edits, and provider proposals use the same delta shape.

`docker compose up --build` starts the local stack. `scripts/demo.sh` bootstraps `fixtures/food-delivery/` inside the backend image into `${DECISION_DEMO_WORKSPACE:-${XDG_CACHE_HOME:-~/.cache}/switchplinth-demo}/food-delivery` with fixture-tuned mock extraction (it shows the decision/option/scenario model, not extraction quality), starts Compose project `switchplinth-demo` on it, rescans to rebuild indexes, and needs only Docker and curl; `--down` stops the stack and deletes its volumes, `--reset` re-creates the sample, and `--purge` also deletes the workspace, including root-owned files the backend writes. Published ports are configurable through `DECISION_FRONTEND_PORT`, `DECISION_BACKEND_PORT`, and `DECISION_QDRANT_PORT`. Compose mounts `${DECISION_WORKSPACE_HOST:-.}` at `/workspace/repos`; `DECISION_WORKSPACE_NAME` (set by `scripts/demo.sh`) names that mounted root in `/api/v1/project` and the repository list, which otherwise report the mount point name `repos`. The repository chooser accepts only relative directories beneath this mount and rejects symlink traversal. It filters generated/hidden folders and lists only directories with Markdown, `.git`, or `.decision`. Opening a Markdown-only repository bootstraps portable v1 schema/config/instructions without imposing an ADR template. SQLite caches and Qdrant collections are namespaced per canonical repository path. Discovery excludes `.decision/`, `.tasks/`, and generated caches by default; `.decision/config.yaml` supports additional path exclusions, source-specific includes such as `extraction.include: [.tasks]`, and a `max_candidates` limit. Excluded task evidence remains unresolved for historical provenance; mixed-support inferred claims, decisions, options, entities, aliases, and evidence-bearing relationships have excluded IDs filtered, and safe task-only inferred records and entirely task-grounded inferred decisions are removed when unselected and unreferenced. Human-reviewed records and review chains are preserved byte-for-byte. Saved scenario selections are matched by `(decision_id, option_id)`, so option IDs reused by different decisions do not cross-reference each other. A scan fails closed if a task-only option is selected or scenario-referenced, if a task-only entity or relationship remains referenced, or if a task-only relationship is used by an active selected option or human-reviewed decision delta. `POST /api/v1/discovery/scan` performs the full Markdown scan and per-repository SQLite/Qdrant rebuild; it restores portable YAML on synchronous exceptions, not abrupt termination or concurrent writes. Corrected aliases/claims use `/api/v1/aliases/{id}/correct` and `/api/v1/claims/{id}/correct`; appended asserted records preserve evidence and supersede original/prior judgments. `GET /api/v1/reviews` returns the human claim/alias/identity review log newest first; `POST /api/v1/reviews/{record_id}/undo` appends an `undoes` record that reverts only the unsuperseded head of a review chain (409 otherwise), is idempotent, and is honored by every effective-state reader (see docs/PORTABLE_FORMAT.md). The Facts page shows this log with each entry's prior state and an Undo action. Confirm, reject, and correct controls remain available on effective human-reviewed claim/alias rows so judgments can be revised again. Structural claims may reference option-created entities; graph projection includes a corrected relationship only in scenarios where both endpoints exist, and reports an invalid assumption otherwise. Identity endpoints must be existing, distinct, same-kind base entities and are validated on save, read, review, and correction. Full cross-record validation runs on reads, not generic saves, so incremental scan/extraction writes remain safe. `model_connection` records may carry an optional additive `generation: {reasoning: off|low|medium|high, max_output_tokens: int, request_timeout_seconds: number}`, validated against the bundled v1 schema on reads and writes. Extraction and delta proposal map it to LiteLLM `reasoning_effort` (`off` becomes `none`; omitted for Anthropic) and `max_tokens`. Blank generation fields are omitted on save; a re-save without `generation` keeps the stored value and an explicit `{}` clears it. The connection form edits `request_timeout_seconds` (0 < n <= 86400), keeps the other stored generation keys, sends `{}` when clearing a stored timeout leaves no other key, and otherwise omits `generation` when the timeout is blank and no other key is stored.

Keyless local `openai_compatible` connections use a placeholder API key for LiteLLM when `credential_ref` is absent; the local service may ignore it. Embeddings and structured extraction share this behavior. Explicit configured credential references continue to resolve from the environment.

For `why` searches about selected choices, the backend reports `grounded: true` only when effective claims cite the returned current passages. When passages exist without claim support, it returns the passages and labels the answer as not fully grounded. A why answer about an option absent from the selected scenario is also grounded when it returns that option's own current, indexed evidence (`context: decision_option`). A selected decision that involves a matched entity answers first, followed by unselected alternatives. An exact entity or alias match on an unselected option yields the unselected-option answer unless the query also names exactly an active entity that a selected decision involves. Generic lexical searches retain passage-based grounding.

`PortableRepository.save()` publishes one YAML record at a time through a same-directory temporary file, flush/fsync, and atomic replace. A process interruption leaves that target as a complete old or complete new record; ordinary exceptions clean up the temporary file, while an abrupt exit before replace can leave a hidden `.tmp` file. This does not make multi-record scan/provider operations transactional, serialize concurrent writers, or guarantee persistence across power loss or storage-cache failure.

Saved scenarios load selections into the current graph and persist only under `.decision/scenarios/`. The Architecture map What-if overlay lets users switch decision options directly; graph, rationale/evidence, and conflict/assumption state update without navigating to Scenarios. Scenario resolution keeps the last resolved selection for Save and grounded search while a new choice is pending; failed resolution restores those choices and leaves the graph intact. Repository switches invalidate pending scenario/list responses. Save includes an optional expected repository root, which the API checks before writing to the service captured by that request. The saved-scenario list reports loading, an empty successful list, or a visible error with Retry; refresh failures retain the last loaded list. Scenario lifecycle currently supports create, list, and load; rename, update, and delete are not implemented and remain a product decision.

When a safely evidence-anchored provider decision fails only because its typed option deltas are invalid, extraction may persist it with empty active deltas and a top-level `extraction_review` audit containing the rejected JSON and validator errors. This metadata is excluded from graph compilation, exposed by `/api/v1/decisions`, and visibly marked in the UI after reload. A validated manual option edit clears only that option's audit item; the audit field is removed when all listed options are resolved. The backend validates this optional additive field against the bundled v1 schema on record reads and writes, even when an existing project has an older permissive overlay schema. That project schema copy remains unchanged and does not independently validate this field; standalone validators need a deliberate schema refresh or migration. Older readers can ignore it, but writers that strip unknown fields can lose the audit. See `docs/PORTABLE_FORMAT.md`.
