# Development notes

Setup, behavior, and verification detail for contributors and coding agents. The README covers the short version. Engineering rules are in [AGENTS.md](../AGENTS.md); the portable file format is in [PORTABLE_FORMAT.md](PORTABLE_FORMAT.md); the architecture is in [ARCHITECTURE.md](ARCHITECTURE.md).

## Names

Earlier revisions used “Decision Graph” as a working title and “Waypoint” as a provisional UI label. The product, Python package and import (`switchplinth`), CLI (`switchplinth`), MCP server name (`io.github.bcmyguest/switchplinth`), and Compose project (`switchplinth`) now use the name Switchplinth. The `DECISION_*` environment variables keep their names. The portable format keeps its `.decision/` directory and `decision/v1` schema version.

Switchplinth turns repository Markdown into a portable, reviewable architecture graph. It discovers ADRs, RFCs, design notes, and other Markdown without requiring a particular template. The source documents and validated YAML under `.decision/` are canonical; SQLite and Qdrant are disposable indexes.

## Demo script

Requires Docker with Compose v2 and curl. No model, credentials, Python, or Node.

```sh
./scripts/demo.sh
```

The script builds the images, copies the fictional food-delivery sample (`fixtures/food-delivery/`) into `~/.cache/switchplinth-demo/food-delivery`, extracts it with fixture-tuned deterministic mock extraction, starts the stack as Compose project `switchplinth-demo`, rebuilds the search indexes, and prints the URL (<http://localhost:3000>). The sample yields 7 decisions and 18 components. `./scripts/demo.sh --down` stops the stack and deletes its volumes; `--reset` re-creates the sample; `--purge` stops the stack, deletes its volumes, and deletes the demo workspace. The backend container runs as root, so once you scan or review in the UI the workspace holds root-owned files; remove it with `--purge`, not `rm`. Set `DECISION_DEMO_WORKSPACE` to choose another directory, and `DECISION_FRONTEND_PORT`, `DECISION_BACKEND_PORT`, or `DECISION_QDRANT_PORT` if 3000, 8000, or 6333 is taken. Stop any other stack on those ports first. The sidebar shows the repository name `food-delivery`.

Earlier revisions named the demo stack `decision-graph-demo` and its workspace `~/.cache/decision-graph-demo`; the current script no longer touches either. Remove them with `COMPOSE_PROJECT_NAME=decision-graph-demo DECISION_DEMO_WORKSPACE=~/.cache/decision-graph-demo ./scripts/demo.sh --purge`.

## Local model connection

Optional: connect a local OpenAI-compatible model server (for example one listening on host port 1234) to try provider extraction:

```sh
curl -X POST "http://localhost:${DECISION_BACKEND_PORT:-8000}/api/v1/connections" -H 'Content-Type: application/json' \
  -d '{"id":"local-model","provider":"openai_compatible","endpoint":"http://host.docker.internal:1234/v1","model":"<your-model-id>","capabilities":{"structured_output":true}}'
```

Then choose **Discover decisions** and select that connection. The connection is saved under the sample's `.decision/`; it needs no API key.

The full connection reference is on the site's [model providers](https://bcmyguest.github.io/switchplinth/docs/providers/) page.

## Run with Docker Compose

Docker Compose starts three services:

```sh
docker compose up --build
```

- Web app: <http://localhost:3000>
- Backend API and OpenAPI docs: <http://localhost:8000/docs>
- Qdrant: <http://localhost:6333>

Published ports bind to `127.0.0.1` by default. The backend container maps `host.docker.internal` to the host gateway so local model servers can be reached from Linux Compose. The API is unauthenticated in V0; external listener access is not configured.

Compose mounts `${DECISION_WORKSPACE_HOST:-.}` at `/workspace/repos` (the current directory by default). The repository chooser lists Markdown repositories under that mounted directory; selected paths are relative, and paths that traverse symlinks or escape the mount are rejected. New Markdown-only repositories receive a portable `.decision/` v1 schema, config, and instructions on first open. To mount a different workspace, set `DECISION_WORKSPACE_HOST` before starting Compose. The container sees the mounted directory as `repos`; set `DECISION_WORKSPACE_NAME` to show its real name in the UI (`scripts/demo.sh` sets it to `food-delivery`).

## Workspace UI

The workspace navigation provides separate **Architecture**, **Architecture log**, **Progress**, and **Facts** pages. Architecture places the Decision assistant near the top of the system map flow. Architecture log lists decisions and links to scenario options; each decision shows its rationale, each alternative's "why not chosen" reason where the source states one, and consequences where present, with passage links, and a previewed What-if alternative is labelled as previewed, not rejected; Progress reports counts from the current graph and Markdown evidence; Facts contains **Needs a closer look** review controls and links back to the system map. Scenarios and Explore retain scenario selection and grounded assistant workflows. The theme control switches between light and dark semantic themes and remembers the choice in the browser. All **Discover** actions (Source Types, the page heading, and the source card) open the same mode choice: deterministic/mock extraction or a configured model connection. Provider mode sends that connection ID to `POST /api/v1/extraction/run`; its result names the provider/model and reports saved record counts or a visible error. After provider records are saved, SQLite and Qdrant are rebuilt from the canonical Markdown and `.decision/` data so search sees the new records. The sidebar’s **Source Types** control opens V0 Markdown source details and the shared Discover action. The UI can inspect inferred entities and evidence, review claims and aliases, switch decision options, edit their shared typed deltas, and resolve a scenario. On the Architecture map, the What-if overlay lets users switch decision options in place; the graph, rationale/evidence, and conflict/assumption state update without navigating to Scenarios. Selecting a map node opens component details beside the map without changing page scroll. The details show rationale and evidence from an option that changes that entity, label unselected option rationale as an alternative, and label other passages as source context. Review controls remain available on human-reviewed rows so judgments can be confirmed, rejected, or corrected again; new records supersede earlier judgments and preserve evidence. Claims may reference entities introduced by option deltas; projection includes those relationships only while both endpoints exist in the selected scenario. Saving a scenario writes its decision selections to `.decision/scenarios/`. A configured model can propose a delta for preview; manual delta edits can also use `POST /api/v1/scenarios/preview-delta` for server validation and scenario resolution without writing `.decision/`. Malformed operations return HTTP 422 before writing canonical files. Accepting the proposal updates the same option delta used by manual editing. Search accepts the current `selections` map so rationale and evidence follow the visible scenario. Without a configured model, proposal returns an unsupported response. Search returns answers only when supporting evidence is available.

## Discovery and scan

The repository chooser filters hidden/generated directories and only lists candidates containing Markdown, `.git`, or `.decision`. The discovery scan excludes `.decision/`, `.decision-cache/`, `.tasks/`, `.pytest_cache/`, and common build/cache directories by default. Add path segments under `extraction.ignore` in `.decision/config.yaml` to exclude more paths. To index task Markdown intentionally, add a source path or directory such as `extraction.include: [.tasks]`; this opts in only that source and does not override other ignored directories. When `.tasks/` is excluded, a scan marks prior evidence unresolved for historical provenance, filters excluded IDs from mixed-support inferred claims, decisions, options, entities, aliases, and evidence-bearing relationships, and removes safe task-only inferred content, including entirely task-grounded inferred decisions when they are unselected and unreferenced. Current-source inferred references can continue supporting a shared entity after task evidence is removed. Human-reviewed records and their review chains stay byte-for-byte unchanged. The scan fails closed when removing a selected or saved-scenario-referenced option, or when a task-only inferred entity or relationship remains referenced, including relationships referenced by active selected options or human-reviewed decision deltas. `extraction.max_candidates` limits inferred decision and candidate-passage output (default 50). `POST /api/v1/discovery/scan` performs discovery, extraction, and a full SQLite/Qdrant index rebuild; SQLite stores its index version, and Qdrant collections are namespaced by canonical repository path. If a synchronous scan operation raises, the backend restores the previous `.decision/` files. Abrupt process or host termination is outside that rollback guarantee.

## Identity links

Identity links use the existing `decision/v1` claim shape with predicate `same_entity_as`; the schema file is unchanged and no migration is needed for this predicate semantic. Schema validation runs on every save, and identity endpoint validation requires existing, distinct, same-kind base entity records on save, read, review, and correction. Full cross-record validation runs on reads, not generic saves, so incremental scan/extraction writes remain safe. `/api/v1/graph`, search responses, and entity details return `identity_groups`, `identity_suggestions`, and `identity_conflicts`. Only unsuperseded human `confirmed` or `asserted` links form symmetric read-time groups; exact-name same-kind matches and inferred identity claims are suggestions. Exact-name candidates normalize case and whitespace. `POST /api/v1/identity-candidates/review` verifies a current exact-name pair and appends a human claim for `confirmed`, `asserted`, or `rejected`, with empty evidence and no source provenance. Repeating the active judgment is idempotent; later judgments supersede prior pair judgments through the review chain, and an unconflicted rejected exact-name pair remains visible as a rejected human judgment with review actions, while a pair already surfaced as a conflict appears only in its conflict card. Search uses full claim history for identity review and conflicts; scenario graph compilation uses effective claims. Unsuperseded opposing human judgments and rejected pairs connected by confirmed paths are reported as conflicts, and conflicted connected components are withheld from groups. Reviews append records using the existing `reviewed_claim`/`supersedes` chain. The frontend shows groups, suggestions, conflicts, pair endpoints, available review state/provenance/evidence in selected entity details and Facts. Inferred-claim suggestions retain confirm/reject and same-kind endpoint correction through the existing claim APIs; exact-name candidates use the pair review operation. Identity review stays separate from alias review. Groups never rewrite entity IDs, aliases, typed deltas, or saved scenario selections, and scenario reads do not restore option-created entities that are absent from that scenario. Any incompatible schema shape change requires an explicit migration.

## Review log

Human reviews form an append-only log. `GET /api/v1/reviews` lists claim, alias, and identity judgments newest first with their effective and undoable state. `POST /api/v1/reviews/{record_id}/undo` appends a record whose optional `undoes` field reverts the current head of one review chain, restoring the prior judgment or original inference; non-head records return 409 and repeats are idempotent. The Facts page shows this log; each entry shows the prior state and an Undo action. See `docs/PORTABLE_FORMAT.md`.

The map visually projects only human-confirmed/asserted identity groups as one logical node. Original entity IDs, aliases, deltas, and scenario selections remain unchanged, and component details expose provenance from every group member. Inferred claims and exact-name matches remain separate. A non-rejected identity candidate may expose related alternatives with its unresolved status visible; human rejection or conflict blocks that navigation.

## Stdio MCP server

The backend package installs one console script, `switchplinth`. Without a command, it serves the HTTP API on port 8000. The `mcp` command serves the same five read-only MCP tools over stdio, with no Docker, Qdrant, or model required:

```sh
cd backend && uv run --locked --python 3.12 switchplinth mcp --repo /path/to/repo [--cache DIR] [--scan]
```

- `--repo PATH`: the repository with Markdown and `.decision/` (default: the current directory). A missing directory exits with an error. Opening a repository creates `.decision/schema/record-v1.schema.json`, `.decision/config.yaml`, and `.decision/instructions.md` when they are absent.
- `--cache DIR`: the disposable SQLite cache directory. The default is `$DECISION_CACHE` or `/tmp/switchplinth-cache`, plus a 16-character hash of the resolved repository path.
- `--scan`: run the deterministic mock extraction scan before serving. It writes inferred evidence, entity, decision, claim, and alias records under `.decision/`. Without `--scan`, startup rebuilds the indexes from existing `.decision/` evidence and writes no records, so an unscanned repository serves an empty graph.

Stdio keeps passage vectors in an in-process index, rebuilt at startup, instead of Qdrant. Unless exactly one non-Anthropic connection sets `capabilities.embeddings: true` with an `embedding_model`, the index uses deterministic token-hash vectors and search reports `semantic_index.mode: deterministic_local`; these vectors are not semantic embeddings. With exactly one such connection, startup and each search call that model; if it is unreachable, vector search reports an error and lexical search still answers.

To register it with an MCP client, use the command above with an absolute `--repo` path, or install the backend wheel and run `switchplinth mcp --repo PATH`. The server reports the MCP name `io.github.bcmyguest/switchplinth` and the package version from `backend/pyproject.toml`. To run it from Docker over the bundled food-delivery fixture, with no network, run `docker build -f Dockerfile.mcp -t switchplinth-mcp .` from the repository root and then `docker run -i --rm --network none switchplinth-mcp`.

## Setup wizard

`switchplinth setup` picks a repository, starts it locally or in Docker, saves an optional model connection, runs the first scan, registers the stdio MCP server with one client, and checks that the server answers. Run it from `backend/`:

```sh
uv run --locked --python 3.12 switchplinth setup                 # asks each question
uv run --locked --python 3.12 switchplinth setup --sample --yes  # food-delivery sample, local mode, print snippets
```

Each flag answers one question; `--yes` takes the defaults for the rest and accepts every confirmation except remounting a running Compose project (see below).

- Repository: `--repo PATH`, or `--sample` for the food-delivery sample. The sample is bootstrapped once at `$DECISION_DEMO_WORKSPACE/food-delivery`, default `${XDG_CACHE_HOME:-~/.cache}/switchplinth-demo/food-delivery`, the same place `scripts/demo.sh` uses, and reused on later runs.
- Mode: `--mode local` (default) opens the repository in-process with the stdio server's SQLite cache and needs no Docker. `--mode docker` builds and starts the Compose stack with the repository mounted, then saves the connection and scans through the HTTP API. `--project` names the Compose project (default `switchplinth-setup`, so it never collides with a plain `docker compose up` in the checkout, which is project `switchplinth`). `--frontend-port`, `--backend-port`, and `--qdrant-port` default to 3000, 8000, and 6333; a new project stops if any port is taken. Docker mode needs the source checkout.
- Model: `--provider none|openai-compatible|openai|anthropic` (default `none`), `--endpoint`, `--model`, `--credential-env NAME`, `--reasoning-off`. The wizard lists the provider's models when it can reach them. It stores the key only as `credential_ref: env:NAME` and rejects anything that is not a variable name. For an OpenAI-compatible server it asks for the variable name, or `none` for a keyless local server. In Docker mode a loopback endpoint is rewritten to `host.docker.internal`, and the provider diagnostics run from inside the backend container.
- Client: `--client claude-code|claude-desktop|cursor|vscode|print`. The default is `claude-code` when the `claude` CLI is on PATH, otherwise `print`, which prints every snippet and writes nothing. `--claude-scope user|local|project` (default `user`) sets the Claude Code scope.
- `--no-scan` and `--no-verify` skip the first scan and the MCP `initialize`/`tools/list` check.

Clients always get the local stdio command (`switchplinth mcp --repo PATH`, or `python -m switchplinth.cli` when the script is not on PATH), in Docker mode too. The container's HTTP `/mcp` is checked separately and is there for clients that speak HTTP.

What it writes:

- `<repo>/.decision/`: the portable files every repository gets on first open, the scan's inferred records, and `connections/` when a model is chosen.
- Local mode: the SQLite cache under `$DECISION_CACHE` (default `/tmp/switchplinth-cache`), namespaced by repository.
- Docker mode: `${XDG_CONFIG_HOME:-~/.config}/switchplinth/compose-<project>.env` with the project name, workspace, and ports, and, when a credential is set, `compose-<project>.override.yml`, which passes that variable from your shell into the backend. Neither file holds a key. The wizard never runs `down` or `prune`; the closing summary prints the stop command.
- Claude Desktop, Cursor, and VS Code: the user-level JSON config (`~/.cursor/mcp.json`; `claude_desktop_config.json` and `Code/User/mcp.json` under `${XDG_CONFIG_HOME:-~/.config}` on Linux or `~/Library/Application Support` on macOS). The wizard shows a diff and asks first, copies the old file to `<file>.<UTC timestamp>.bak`, replaces only the `switchplinth` entry, and writes atomically. A file that is not valid JSON stops setup with nothing written.
- Claude Code: the wizard runs `claude mcp get`, then `claude mcp add --scope <scope>`, after `claude mcp remove` from the scope the existing entry uses when that entry differs. Claude Code's own CLI writes its config, so the wizard takes no backup.

A rerun with the same answers changes nothing: the sample is reused, an identical client entry is left alone, and a running project on the same workspace goes through `docker compose up` again with the same settings. If the target Compose project is already running with a different workspace, an interactive run asks before restarting it; with `--yes` it stops unless you pass `--replace-workspace`.

On Windows the wizard writes no client config and runs no client CLI, `claude` included: every client prints its snippet or command for you to add. Docker mode is refused there; start the stack by hand with `docker compose up --build` and `DECISION_WORKSPACE_HOST`, or use `--mode local`.

Exit codes: 0 when every step passed, 1 when a check failed or you declined the plan, 2 when setup stopped with a message, and 130 on Ctrl-C.

## Portable data and generated state

Markdown and `.decision/` YAML are portable project data. Provider credentials are referenced through environment variable names such as `env:MODEL_API_KEY`; secret values are not written to YAML. Local `openai_compatible` endpoints may omit `credential_ref`; an explicit `env:` reference is preserved and used when configured. Blank optional connection fields are omitted from saved `model_connection` records. Inferred records retain evidence anchors and confidence, and human reviews are appended as superseding records.

SQLite is stored in the `decision-cache` volume and Qdrant data in `qdrant-data`. Both are rebuildable. `docker compose down -v` removes those generated volumes; it does not remove repository Markdown or `.decision/` files.

## Development checks

```sh
cd backend && uv run --locked --python 3.12 pytest -q
cd frontend && pnpm install --frozen-lockfile && pnpm typecheck && pnpm lint && pnpm build
```

The backend exposes deterministic mock extraction and a LiteLLM adapter for configured providers. Local `openai_compatible` endpoints can perform structured extraction and configured embeddings without an API key; hosted OpenAI and Anthropic connections still use their configured credentials. Provider extraction requests typed option deltas using the supported entity and relationship operations, including optional `expect: {}` or `expect: {exists: boolean}` preconditions; when a safe typed operation cannot be formed, the prompt requests `operations: []`. Unsupported or malformed generated operations trigger one bounded retry with schema feedback. The prompt lists known entity IDs with names. A relationship endpoint that names exactly one entity or alias (case- and whitespace-normalized), including an entity returned in the same response or added by the same delta, is mapped to that entity's ID before validation; ambiguous names, and unknown references while any entity is known, join the same retry with the valid ID/name list. References are never guessed. An invalid `alias_confidence` falls back to 0.65 with a diagnostic instead of rolling back the extraction. Invalid or ambiguous selections are rejected without coercion. If a record remains invalid after the bounded retry and the safely anchored-decision fallback is ineligible, it is not persisted and its diagnostic appears in the extraction completion summary; generated deltas are not otherwise rewritten. Repeated inferred decisions are collapsed only when the exact evidence anchor, complete normalized option labels, and selected label identify one unambiguous existing inferred record. Ambiguous same-passage candidates remain available for human review. Configure `embedding_model` with `capabilities.embeddings: true` to use provider embeddings for both Qdrant indexing and querying. Without that configuration, V0 reports that provider embeddings are unsupported and uses deterministic token-hash vectors as an offline fallback; those vectors are not semantic embeddings. A connection's optional `generation` object sets `reasoning` (`off`, `low`, `medium`, or `high`), `max_output_tokens`, and `request_timeout_seconds` (default 600) for extraction and delta proposal; for example `"generation":{"reasoning":"off"}` stops local reasoning models such as Qwen on Lemonade from spending the whole output budget on hidden reasoning and returning empty content. See `docs/PORTABLE_FORMAT.md` for the LiteLLM mapping. The connection form edits only `request_timeout_seconds` and keeps the other stored `generation` keys; set `reasoning` and `max_output_tokens` through `POST /api/v1/connections` or the YAML record, and send `"generation":{}` to clear the object. On hosted reasoning models `off` may be rejected, and hosted behavior is unverified. Use connection diagnostics to inspect endpoint and model connectivity before running provider extraction or proposal. For an HTTP-level check, the backend exposes `/health`, OpenAPI at `/docs`, and MCP streamable HTTP at `/mcp`. MCP provides `list_decisions`, `search_decisions`, `inspect_architecture`, `inspect_entity`, and `diff_scenarios`; HTTP `/mcp` and `switchplinth mcp --repo PATH` (stdio) expose the same tools. Stdio uses an in-process vector index instead of Qdrant but still calls a configured embedding model. Each tool accepts an optional `selections` map from decision ID to option ID.

### Frontend layout

`frontend/src/App.tsx` is a shell: it creates the controllers and mounts the pages and dialogs. Controllers are hooks that receive their dependencies as arguments and return one object; views receive controllers as props.

- `app/`: hash navigation, theme, the workspace core (`useWorkspace`: graph, liveness, project, label catalog, repository generation), sidebar, top bar, and page heading.
- `features/architecture/`: Architecture page, map canvas, overlay panels (`useArchitecturePanels`), component detail, and map actions.
- `features/scenarios/`, `features/graph-editor/`, `features/facts/`, `features/explore/`, `features/discovery/`, `features/evidence/`, `features/settings/`, `features/repository/`, `features/architecture-log/`, `features/progress/`, `features/review-log/`: one feature each.
- `map/`: ReactFlow projection, layout, node and edge components, and the map and full-screen hooks.
- `components/`: shared UI. `components/ui/` holds the primitives (Alert, Badge, Button, Card, Dialog, Input, Radio, Select, Textarea); Button variants (`choice`, `subtle`, `icon`, `link`, `outline`) carry the shared control styling; call sites add layout and local overrides. `components/InlineError.tsx` is the request-error line with an optional recovery action.

A repository switch (`features/repository/useRepositorySwitch.ts`) calls each feature controller's `reset()` after the project opens; a failed open resets nothing.

## Scenarios

Saved scenarios load selections into the current graph and persist only under `.decision/scenarios/`. Scenario resolution keeps the last resolved selection for Save and grounded search while a new choice is pending; failed resolution restores those choices and leaves the graph intact. Repository switches invalidate pending scenario/list responses. Save includes an optional expected repository root, which the API checks before writing to the service captured by that request. The saved-scenario list reports loading, an empty successful list, or a visible error with Retry; refresh failures retain the last loaded list. The current scenario lifecycle supports create, list, and load; rename, update, and delete are not implemented and remain a product decision.

The Architecture map's What-if panel treats option changes as a temporary working preview and provides a one-click return to the repository's selected choices. It keeps the base choices and up to four recent resolved combinations in session-only history; selecting a history entry resolves that exact combination again, and switching repositories clears the history. A sticky decision picker stays available while browsing the option list; choosing a decision scrolls its choices and source into view and focuses the active choice. The panel shows two comparisons, each labeled with its baseline. **Changes vs previous choice** (`features/scenarios/PreviousChoiceDiffPanel.tsx`) compares the last switch with the selection resolved just before it. It lists switched decisions; added, removed, and changed components and relationships by display name; conflicts and invalid assumptions that appeared or disappeared; and affected decisions with reasons. **Affected downstream** lists that diff's `impact` items, each with dependents, depth, a path of names, and a text status: `Dangling` or `Rewired` when one of its own edges lost its target; otherwise `Direct` at depth 1, where its own edge is the removed or replaced relationship or points at the replaced entity, and `Indirect` deeper, plus one line stating the limits. The preview summary at the top leads with the last switch's change count when a previous-choice comparison is ready, then the counts against repository choices. When the selection did not change, the panel says so and skips the empty groups. **Compared with repository choices** keeps the earlier outcome: changes, affected decisions, and assumptions relative to the repository-selected options. `usePreviousChoiceDiff` owns the request: each switch hides the old diff, and a response is dropped when a newer switch, a cancelled resolve, a delta-editor commit, a rebase, or a repository switch has superseded it. Failures show an inline error with Retry. `scenarioDiff.ts` turns the response into strings, naming IDs through the label catalog and relationship kinds from the graphs before and after the switch. The demo graph (no backend) shows no previous-choice comparison. **Save or reopen a named scenario** is a secondary action; saved scenarios persist under `.decision/scenarios/` and can be reopened from the same panel.

## Scenario diff, impact, and receipts

`POST /api/v1/scenarios/diff` takes `{"before_selections": {...}, "after_selections": {...}}` (decision ID to option ID; an empty or omitted map means the repository-selected options) and compares any two scenarios. MCP `diff_scenarios` takes the same two arguments and returns the same JSON. Both scenarios go through the same projection as `/api/v1/scenarios/resolve`; `backend/src/switchplinth/scenario_analysis.py` only compares the two compiled graphs. The response holds:

- `selections.before` and `selections.after`: the resolved full maps; `selection_changes`: `[{decision_id, before_option, after_option}]`.
- `entities` and `relationships`, each `{added, removed, changed}`. Entities carry `id`, `kind`, `name`, `description`; relationships carry `id`, `from`, `to`, `kind`, `claim_id`; a changed item is `{id, before, after}`.
- `conflicts`, `invalid_assumptions`, and `unmet_requirements`, each `{appeared, disappeared}`. Unmet requirements are matched by requirer and capability; `capability_limits` states the rule.
- `affected_decisions`: `[{id, title, reasons}]`, where `reasons` holds `selection_changed` and/or `options_reference_changed_elements` (an option of that decision writes or connects a changed ID).
- `impact` and `receipt`, described below.

`impact` lists, for each element the after scenario removes or replaces, the entities that depend on it: `{basis, max_depth, limits, items: [{type, id, name, change, dependents, truncated}]}`. A relationship's source depends on its target. Dependents come from a breadth-first walk against relationship direction over the before scenario's relationships, up to `max_depth` hops (4); `truncated: true` means more dependents lie beyond the cap. Each dependent has `entity_id`, `name`, `depth`, `path` (alternating entity and relationship IDs, ending at the item), `present_after`, `points_at_missing`, `rewired`, and `missing_endpoints`. `missing_endpoints` lists the dependent's outgoing before-scenario relationships whose target is absent after the switch, as `[{relationship_id, kind, missing_entity_id, status, rewired_to}]`. `status` is `rewired` when the after scenario gives the same source a relationship of the same kind to a target it did not reach with that kind before (`rewired_to: [{relationship_id, to}]`), and `dangling` otherwise. `points_at_missing` is true when any entry dangles; `rewired` is true when any entry is rewired. `rewired` is a heuristic. `scenario_analysis.option_replacements` limits candidate replacements for a lost edge to relationship IDs that the newly selected option of a switched decision adds or replaces, where some option of that decision references the missing target. An edge added by an unrelated decision therefore cannot hide a dangling dependency. The heuristic still does not check that the option intended a replacement, and several lost same-kind edges from one source can share one replacement. Calling `downstream_impact` without `replacements` accepts any new same-kind edge. In the food-delivery Kafka-to-SQS switch, Order Service lost `publishes_to` the Kafka stream and is `rewired` to the SQS stream, so `points_at_missing` is false. Items are removed/replaced entities first, then removed/replaced relationships whose endpoints both survive; a relationship removed with its endpoint entity is covered by that entity's item. Ordering is by ID, then depth and entity ID, so output is deterministic. Impact is relationship-based only: it sees the declared and claim-derived relationships in the graph, not code, runtime traffic, or undeclared dependencies. Every kind is read source-depends-on-target, so `communicates_with` is not treated as symmetric and `implements` makes the implementer depend on what it implements. It uses source entity IDs and does not traverse `same_entity_as` identity groups, so a dependent attached to another member of a confirmed group is missed. `POST /api/v1/scenarios/resolve` returns `impact` of its selections against the repository-selected options; `GET /api/v1/graph` and MCP `inspect_architecture` carry it as `scenario.impact`; at the repository-selected options it is empty and skipped. `DecisionService.graph_json(selections, annotate=False)` omits `receipt` and `scenario.impact`; `GET /api/v1/decisions`, entity detail, the setup summary, and the delta-proposal prompt use it.

`unmet_requirements` comes from `scenario_analysis.capability_check`, which reads `requires_capability`, `provides_capability`, and `lacks_capability` claims (see `docs/PORTABLE_FORMAT.md`). A requirement is met when the requirer, or an entity it reaches by following the scenario's relationships from source to target within four hops, has an effective `provides_capability` claim for that capability. Each unmet item has `requirer`, `requirer_name`, `capability`, `capability_name`, `requirement_claim_ids`, `evidence`, `unreachable_providers` (active providers outside the requirer's reach), and `lacking` (reachable entities with a `lacks_capability` claim, each with its `path`, `claim_ids`, and `evidence`). A lack claim never cancels a reachable provider. Rejected and superseded claims are ignored, `same_entity_as` groups are not traversed, and nothing checks the claims against real technology behaviour. `POST /api/v1/scenarios/resolve` returns `unmet_requirements` at the top level; `GET /api/v1/graph`, `/resolve`'s `graph`, and MCP `inspect_architecture` carry it as `scenario.unmet_requirements`. In the food-delivery sample, mock extraction reads "The Order Service requires replay", "Kafka supports replay", and "SQS does not support replay" from `decisions/event-transport.md`. Switching the event transport from Kafka to SQS therefore reports Order Service's replay requirement under `unmet_requirements.appeared`, citing Amazon SQS through the SQS stream and listing Apache Kafka as an unreachable provider. The mock rule takes the subject from the first catalog entity named in the same sentence and recognizes only the terms replay, ordering, and deduplication after explicit verbs (requires, needs, must ... support; supports, provides; does not support, cannot, lacks).

A `receipt` stamps the canonical inputs behind a result. It appears in `GET /api/v1/graph`, `POST /api/v1/scenarios/resolve` (top level and `graph.receipt`), `POST /api/v1/search`, `POST /api/v1/scenarios/diff`, and MCP `list_decisions`, `inspect_architecture`, `search_decisions`, and `diff_scenarios`. Shape: `{algorithm: "switchplinth-receipt/v1", digest, components: {records, review_heads, evidence_anchors, selections, request?}, record_count, selections, request?}`. `backend/src/switchplinth/receipt.py` computes each component as `sha256:` over canonical JSON (sorted keys, compact separators, UTF-8):

- `records`: the sorted `[folder, id, sha256(record)]` list over every YAML record in `.decision/` `aliases`, `claims`, `decisions`, `entities`, `evidence`, and `relationships`.
- `review_heads`: sorted `[folder, id, epistemic_state]` of human claim/alias judgments that are neither superseded nor undone.
- `evidence_anchors`: sorted `[id, source path, normalized_passage_sha256, state]`.
- `selections`: the resolved selection map (repository defaults merged with the request), echoed in `selections`; for a diff, `{before, after}`.
- `request`: extra inputs, such as `{"query": ...}` for search.

`digest` hashes `{algorithm, components}`. It never reads SQLite, Qdrant, the clock, or process state, so an index rebuild, a new cache, or another process yields the same digest. To check staleness later, repeat the same call (same tool, selections, and query) and compare `receipt.digest`; equal means the canonical inputs are unchanged, and a differing component names the input class that changed. An explicit default selection and an omitted one yield the same receipt. Limits: search ranking also depends on the disposable index and any configured embedding model, which the receipt does not cover; connections, `config.yaml`, and saved scenarios are not hashed; the receipt hashes the same records the call read to build its graph, so a later write cannot make them disagree, but the graph reads its six folders one after another, so a concurrent multi-file write can still be seen half-applied, as with every read.

## Why-search grounding

For `why` searches about selected choices, the backend reports `grounded: true` only when effective claims cite the returned current passages. When passages exist without claim support, it returns the passages and labels the answer as not fully grounded. A why answer about an option absent from the selected scenario is also grounded when it returns that option's own current, indexed evidence (`context: decision_option`). A selected decision that involves a matched entity answers first, followed by unselected alternatives. An exact entity or alias match on an unselected option yields the unselected-option answer unless the query also names exactly an active entity that a selected decision involves. Entity and alias routing requires a complete multiword name, while single-word aliases remain searchable. Generic lexical searches retain passage-based grounding.

## Extraction review fallback

Provider extraction preserves a safely evidence-anchored, selected decision when generated typed option deltas fail validation: it stores empty active deltas and an `extraction_review` audit with the rejected JSON and validator errors. `/api/v1/decisions` exposes the review state, and the UI marks the decision and affected options after reload. A validated manual option edit clears only that option's audit item; the review flag remains until all listed options are resolved. The backend validates this optional field against the bundled v1 definition even when an existing repository has an older schema copy; it leaves that project file unchanged, so standalone validators need a deliberate schema refresh or migration. Older readers may ignore the field, while older writers that rewrite records can discard it; see `docs/PORTABLE_FORMAT.md`.
